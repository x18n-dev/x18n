# 09 - UI

Package `@x18n/ui`. Two halves:

- **Node side** (`src/node`): `createX18nDevframe(projects)` returns a devframe definition that registers RPC functions over loaded projects. It also takes a loader `(ctx) => Promise<projects>`, for hosts that set the devframe up from their own root. Built with tsdown.
- **Browser side** (`app/`): Nuxt SPA (`ssr: false`, nitro `static` preset, `app.baseURL: './'`; Nuxt still renders `/_nuxt/` into the HTML, so a nitro `prerender:generate` hook makes those URLs relative), UnoCSS with its own tokens (preflights in `uno.config.ts`), `@vueuse/core`. Built to `dist/public`, served as devframe `clientAssets`.

The pattern follows `eslint-config-inspector` and `node-modules-inspector`.

## Four modes, one SPA

| Mode | Backend | Writes | Started by |
| --- | --- | --- | --- |
| Dev server | devframe WebSocket RPC to a Node `Project` | yes | `x18n ui` |
| Static report | devframe static RPC dump | no | `x18n build`, deployed anywhere |
| In-browser workspace (1.x) | `Project` running in the page (core + builtins + browser host) | yes, to the opened folder | docs site `/play`, or `x18n build --workspace` |
| VS Code | Same as dev server, server hosted by the LSP | yes | `x18n.openUi` |
| DevTools panel | Same as dev server, hosted by the app's Vite dev server | yes | `@x18n/devtools` in Vite DevTools, Nuxt DevTools or a devframe hub |

The SPA talks to one interface, so pages do not know the mode:

```ts
interface UiBackend {
  readonly mode: 'server' | 'static' | 'local'
  readonly capabilities: { write: boolean, reviews: boolean, openInEditor: boolean }
  project: () => Promise<ProjectSummary>
  keys: (query: KeyQuery) => Promise<KeyPage>
  key: (key: KeyString) => Promise<KeyInfo>
  usages: (query: UsageQuery) => Promise<UsageWithSnippet[]>
  analysis: () => Promise<AnalysisSummary>
  explain: () => Promise<ProjectExplanation>
  translatePrompt: (input: PromptInput) => Promise<string>
  plan: (ops: EditOp[]) => Promise<PlanSummary>
  apply: (plan: PlanId, answers?: Answers) => Promise<ApplyResult>
  review: ReviewApi
  openInEditor?: (location: Location) => Promise<void>
  onChange: (cb: (change: ChangeSummary) => void) => () => void
}
```

- `server` and `static` are backed by `devframe/client` (`connectDevframe`). In static mode devframe already returns dumps; the UI hides edit controls when `capabilities.write` is false.
- `local` calls `@x18n/core` directly. devframe has no in-page RPC backend, so this adapter is ours. The RPC functions and the local adapter both call the same core functions, which keeps their results equal; a test runs the same queries through both and compares.

## RPC functions

Namespace `x18n:`. Types are registered through devframe's `DevframeRpcServerFunctions` augmentation.

| Name | Type | Agent tool | Dumped in static build |
| --- | --- | --- | --- |
| `x18n:project` | static | yes | yes |
| `x18n:keys` | query | yes | yes, one dump for the full list; the UI filters on the client in static mode |
| `x18n:key` | query | yes | yes, per key (sharded) |
| `x18n:usages` | query | yes | yes |
| `x18n:analysis` | query | yes | yes |
| `x18n:explain` | static | yes | yes |
| `x18n:translate-prompt` | query | yes | no (needs live state) |
| `x18n:plan`, `x18n:apply` | action | `apply` yes, with plan review | no |
| `x18n:reviews` (writes go through `x18n:apply`) | query | yes | yes |
| `x18n:open-in-editor` | action | no | no |

Shared state `x18n:state` holds `{ revision, changedKeys }`, so every open tab refreshes after an edit from any surface.

Snippets for usages (a few lines around each usage, highlighted with shiki in the browser) are computed on the node side and cached per file revision.

## Pages

| Route | Content |
| --- | --- |
| `/` | Overview: coverage per locale, diagnostics by check, recent changes, detected presets. |
| `/keys` | Virtualized grid: one row per key, one column per locale (choose and reorder). Inline edit, keyboard navigation like a spreadsheet, filter by namespace, missing in locale, unused, diagnostics, review state; fuzzy search over keys and values. Bulk actions: delete, move to namespace, copy translate prompt for the selection. |
| `/keys/:key` | Key detail: values per locale with placeholder highlighting, usages with code snippets and "open in editor", diagnostics with fixes, review thread, suggestions. |
| `/locales/:locale` | Progress, missing and empty keys, "copy translate prompt" for this locale, placeholder problems. |
| `/usages` | Usage report: missing keys (used, not defined), unused keys, dynamic prefixes. |
| `/extract` | Hard strings per file, proposed keys, edit the plan, apply. |
| `/reviews` | Open threads, requested changes, suggestions to apply. |
| `/project` | `explain()`: presets and why, finders and files, formats, scanners, resolved config with origins. |

## Design

- The look follows [furifont](https://github.com/antfu/furifont)'s app: black and white, square corners, 1px guide lines with crosshairs where they meet, mono uppercase labels. Colors are only for status (errors, warnings, placeholders, complete).
- Every color is a CSS variable in the `uno.config.ts` preflight, with light, `.dark` and `.high-contrast` sets, mapped to semantic shortcuts (`bg-base`, `color-muted`, `border-base`, `btn-outline`, `label`). No design-system dependency: the primitives live in `app/components/ui/`, and `FileIcon` / `FilePath` are adapted from `@antfu/design`, with catppuccin file icons. Phosphor icons via `i-ph-*`.
- A locale bar under the header toggles which locales the views show: grid columns, key detail rows and overview coverage. Its chips reorder by dragging (or Alt and an arrow key), and that order is the column order everywhere. The hidden set and the order are kept per project in `localStorage`, so a new locale shows up by default, in its default place.
- Locales show a round flag from `circle-flags`, of the region in core's `LocaleSummary.flag` (which `localeInfo` in the config can set). The flag set loads on first use, since codes are only known at runtime; a button in the locale bar turns flags off.
- Dense tool UI: keyboard first, no marketing layout.
- The UI is localized with x18n itself (dogfooding): its own messages are JSON files under `app/locales/` in English (the source), Simplified and Traditional Chinese, Japanese, Korean, German, French, Spanish, Brazilian Portuguese and Russian. `x18n check --strict` on the repo runs in CI, so a missing translation, a placeholder mismatch or an unused key fails it. The root `x18n.config.ts` carries a glossary of the [glossary](./glossary.md) terms for `x18n prompt translate`.
- The UI picks its language from `?lang=`, then the visitor's pick in the header (kept in `localStorage`), then the browser's languages. Messages have no plural forms: counts read as `Errors: {count}` or `Missing ({count})`, so no noun agrees with a number. Numbers and percentages are formatted for the UI locale.

## Auth

`x18n ui` can write files, so devframe auth is always on, even on loopback:
- The CLI prints the OTP code and opens the browser with a magic link that authenticates in one click.
- The VS Code panel uses a token issued by the LSP (`x18n/openUi`).
- HTTP MCP at `/__mcp` needs the bearer token that `x18n ui` prints. `x18n mcp` over stdio needs none.
- Static builds have no backend and no auth.
- `--no-auth` exists for CI and e2e only, and prints a warning.

## Static build

`x18n build` calls devframe `createBuild` with `mode: 'build'`, which runs `setup` and dumps the `static` and `query` functions above. Output is a folder that works under any base path. Intended uses: a CI artifact or GitHub Pages report per PR, and a read-only view for translators.

## In-browser workspace (1.x)

- Built into the docs site at `/play` ([16-docs.md](./16-docs.md)).
- "Open folder" uses `showDirectoryPicker()` (Chromium). Other browsers get the demo fixtures in a memory host, or a zip upload.
- The project runs in a Web Worker. Scanners use WASM builds (`@oxc-parser/wasm`); Node-only plugins are skipped with a notice.
- Config: YAML and JSON configs load directly. TS configs need a bundler, so the workspace reads them only when they import nothing but `x18n` (checked with a static parse); otherwise it asks the user to add an `x18n.config.yml`.

## DevTools panel

`@x18n/devtools` mounts the same devframe inside a host's devtools:

- `@x18n/devtools/vite`: `X18nDevtools(options)`, a Vite plugin built with `createPluginFromDevframe` from `@vitejs/devtools-kit`. Vite DevTools adds an iframe dock from the definition's id, name and icon, and serves the SPA at `/__x18n/`. Nuxt DevTools 4 runs on Vite DevTools, so the same plugin works through `vite.plugins`. The plugin disposes the projects in `closeBundle`, which Vite also runs when the dev server closes or restarts.
- `@x18n/devtools/devframe`: `createX18nDevframe(options)`, a devframe definition for `initHub`, `viteDevframeHub` or any other hub.
- Both load the workspace from `ctx.cwd` (the Vite root) and search upward for a config, unless `root` is set. They watch files only in `dev` mode.
- The host owns auth: one gate for every panel. Writes stay on.

## VS Code embedding

See [08-vscode.md](./08-vscode.md) and [07-lsp.md](./07-lsp.md). The UI reads `?theme=` and `?lang=` (`vscode.env.language`), and listens to parent `postMessage` for theme updates. The `openInEditor` capability is on only in this mode and in the dev server with a configured editor (devframe `service-open`).
